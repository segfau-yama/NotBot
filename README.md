# NotBot

Nifty Online Tokensを管理するDiscord Botです。メッセージ・リアクションによるNOTの増減、ギルド内の残高・ランキング、Discord内で完結するコンテンツ売買を予定しています。

P07〜P13のDiscord接続・残高操作、出品・購入・DM配送・無料再送、商品管理・返金、活動・通話の報酬・罰則・譲渡、ロール販売・復旧を実装しています。自動検証済み・実機確認待ちです。次はテスト用サーバーで各工程の実機確認を行います。

## 起動

Rust 1.94以降を用意し、設定例をコピーしてBotトークンを入力します。

```sh
cp .env.example .env
# .env の DISCORD_TOKEN に実際のBotトークンを設定
set -a
. ./.env
set +a
cargo run --locked
```

起動時に設定・SQLiteを初期化し、`/not`・`/content` をグローバル登録してDiscordへ接続します。同名のコマンドを更新し、他のコマンドは置換しません。Ctrl-CまたはSIGTERM（Unix）でGatewayを終了し、DBを閉じます。トークンやDiscordのエラー本文はログへ出しません。

環境変数の `DATABASE_PATH` と `CONTENT_DIR` は省略すると `data/notbot.sqlite` と `data/content` を使います。`SHOP_CHANNELS` は `ギルドID=チャンネルID` をカンマ区切りで指定します。Discord IDは10進数の文字列です。チャンネル対応は省略でき、P07の残高コマンドには不要です。

DBファイルと親ディレクトリは自動作成します。8テーブル・3VIEW・取引理由の初期値は同じトランザクションで初期化し、再起動時はSQLiteの `user_version` で適用済みかを判定します。現在の版は2で、版1のDBには報酬の処理結果テーブルだけを追加し、既存の残高・商品・購入履歴を保持します。DBは実ファイルを使い、`:memory:` は受け付けません。WALモードで動かし、SQLiteのロック待機時間は5秒に設定しています。ロック競合は `Conflict` として返します。

```dotenv
DISCORD_TOKEN=
DATABASE_PATH=data/notbot.sqlite
CONTENT_DIR=data/content
SHOP_CHANNELS=123456789012345678=234567890123456789
```

テストはBotトークンなしで実行できます。

```sh
cargo test --locked
cargo clippy --locked --all-targets -- -D warnings
```

## Discordの設定と残高コマンド

1. [Developer Portal](https://discord.com/developers/applications)でテスト用アプリケーションとBotを作り、Botトークンを `.env` に設定します。
2. InstallationでGuild Installを有効にし、`bot`・`applications.commands` スコープでテスト用サーバーA・Bへ招待します。Botへ管理者権限は不要です。テスト用テキストチャンネルで「チャンネルを見る」を許可し、利用者には「アプリコマンドを使う」を許可してください。P07はInteractionへの返信だけを使い、通常投稿・添付・ロール管理のBot権限はまだ使いません。IDを直接指定する場合はDiscordの「詳細設定 → 開発者モード」を有効にし、各サーバーの「サーバーIDをコピー」を使います。
3. Privileged Gateway Intentsはすべて無効のままにします。P07は `GUILDS` だけを要求し、ギルド名の候補表示にSerenityのキャッシュを使います。所属は単一メンバーのREST取得で確認し、メンバー一覧取得・メッセージ本文の受信は行いません。[Gateway Intent](https://docs.discord.com/developers/events/gateway#gateway-intents)、[メンバー取得](https://docs.discord.com/developers/resources/guild#get-guild-member)
4. `cargo run --locked` で起動します。WebhookではなくGatewayで受信するため、Interactions Endpoint URLは設定しません。グローバルコマンドはギルドとBotのDMコンテキストを有効にしています。反映後にBotのプロフィールからDMを開いてください。[コマンドの登録・コンテキスト](https://docs.discord.com/developers/interactions/application-commands)

```text
# サーバー内（guild省略で現在のサーバー）
/not balance
/not ranking
/not adjust user:@対象ユーザー amount:1200

# BotとのDM（guild必須、候補の選択またはサーバーIDの直接入力）
/not balance guild:123456789012345678
/not ranking guild:123456789012345678
/not adjust user:@対象ユーザー amount:1200 guild:123456789012345678
```

`balance` は本人の残高、`ranking` は履歴のある上位10人をEmbedで表示します。返信は実行者だけに表示し、ユーザーへの通知メンションは発生させません。サーバー内から別サーバーへの操作は拒否します。

`adjust` は対象サーバーの所有者または `ADMINISTRATOR` を持つメンバーだけが使えます。`MANAGE_GUILD` だけでは許可しません。共通の `/not` を一般ユーザーも使うため、調整サブコマンドは表示されても実行時に認可します。対象ユーザーにも同じサーバーへの所属を要求します。`amount` は増減額で、`100`・`+100` は100 NOT加算、`-100` は100 NOT減算、`0` は増減なしの記録になります。指定できるのは-9223372036854775808〜9223372036854775807の整数文字列です。残高が負になる減算や整数上限を超える加算は、履歴を残さず拒否します。DiscordのINTEGERの上限を避け、丸めず検証します。旧 `/not penalize` は `/not adjust` に統合しました。Bot再起動でコマンド定義を更新します。

DM候補にはBotと本人の所属を確認できたサーバーだけを表示し、調整の候補には管理権限も要求します。候補表示は2秒以内に確認できた最大25件です。多数のサーバーやAPIの混雑で候補が出ない場合は、名前の一部・IDで絞り込むかIDを直接入力してください。直接入力でも、実行時にBotの参加・本人の所属・最新ロールを再確認します。

残高・ランキング・残高調整・譲渡は青色のEmbedで表示し、サーバー名・ユーザー・金額を項目ごとに分けます。金額は太字で強調し、ランキングは順位別、調整・譲渡の取引IDはフッターに表示します。購入一覧は `サーバー: サーバー名` と表示します。名前はDiscordから取得し、名称変更は次の操作から反映します。

## 残高操作

`infrastructure::sqlite::not::NotRepository::new(database)` に `SqliteDatabaseAccess` を渡して使います。

- `get_balance(actor)`：実行者の対象ギルドでの残高。履歴がなければ0。
- `get_ranking(actor, limit)`：対象ギルドの残高降順。同額は保存されたユーザーID文字列の昇順。履歴のないユーザーは含めず、件数0は空の一覧。
- `adjust_amount(actor, user_id, amount, request_id)`：管理者が正負の `NotAmount` を指定し、現在残高へ加算・減算します。`/not adjust` はこの操作を使います。
- `adjust_balance(actor, user_id, target_balance, request_id)`：管理者が0以上の目標残高を指定し、現在との差額だけを追記。差額0も記録します。

調整の再試行では同じ依頼IDを使います。同じギルド・対象ユーザー・増減額（`adjust_balance` は目標残高）なら元の取引を返し、追加反映しません。対象や金額を変えて同じIDを使うと `RequestConflict` になります。後から別の取引があっても、過去の依頼を再反映しません。

`Actor` はRepositoryが認証済みの所属・権限から生成する契約です。`infrastructure::discord` がDiscordのREST照会結果から生成し、上記コマンドをSQLite Repositoryへ接続します。

## 報酬・罰則・NOT譲渡（P12）

```text
# サーバー内。BotとのDMでは guild:サーバーID を追加する
/not adjust user:@対象ユーザー amount:-100
/not transfer user:@受取先 amount:500
```

罰則として減算する場合も、管理者が `/not adjust` に負の増減額を指定します。残高50に `-100` を指定すると拒否し、`-50` なら0になります。`transfer` は本人の残高から、同じサーバーのメンバーへ100・500・1,000 NOTを譲渡します。本人・対象の所属をRESTで照合し、自己譲渡・残高不足・受取側の残高上限超過を拒否します。BotからDiscordのタイムアウト処分を実行するコマンドではありません。

`NotRepository.adjust_amount(actor, user_id, amount, request_id)` は取引を1行、`transfer(actor, recipient, amount, request_id)` は送信・受信の順で `(LedgerEntry, LedgerEntry)` を返します。どちらも同じImmediateトランザクション内で依頼の重複と残高を照合し、譲渡は送受信の2行を一括確定します。DBスキーマや依存ライブラリは追加していません。

増減指定のキーは `adjust-amount:{request_id}`、譲渡は `transfer:{request_id}:sent`・`:received`。DiscordではInteraction IDを依頼IDとし、同じ依頼の再処理・再起動後の再試行では元の取引を返します。依頼IDを別の対象・金額に使うと拒否し、片側しかない譲渡履歴は不正データとして扱います。ログの `adjustment_requested`・`transfer_requested` は依頼の受付であり、決済成功の証拠ではありません。結果不明のときは新しいコマンドで再送せず、管理者が `request=` とイベントキーで履歴を照合してください。旧 `penalty:`・`adjust:` の取引履歴はそのまま保持します。

承認済みの報酬ルールに従い、サーバー内の活動へ以下のNOTを付与します。

| 行動 | 受け取れるNOT |
|---|---:|
| メッセージを投稿する | 投稿者に5 NOT |
| 他人の投稿にリアクションする | リアクションした人に1 NOT |
| 自分の投稿にリアクションされる | 投稿者に10 NOT |
| 自分の投稿に返信される | 返信先の投稿者に20 NOT |
| サーバーの通話に参加する | 完了した1分ごとに1 NOT、1日最大300 NOT |
| コンテンツ・ロール商品が購入される | 出品者に販売価格分 |

DM・Bot・Webhook・システム投稿・自己リアクション・自己返信は活動報酬の対象外です。自己返信、BotやWebhookへの返信は投稿報酬も発生しません。通常の返信では投稿者と返信先にそれぞれ別種の報酬を判定します。各受取人のサーバー所属をRESTで確認し、投稿本文は読まず、メッセージID・投稿者・参照先の情報を使います。変更前に付与済みの1 NOTはそのまま保持し、同じイベントの再配信でも増額しません。新しい額はBot再起動後の未処理イベントに適用します。

投稿・リアクション・返信の制限は**サーバー・受取人・報酬種別ごとに60秒に1回、1日100回まで**です。Botでの受付時刻を使い、日本時間00:00で日次上限をリセットします。日付が変わっても60秒の間隔は維持します。制限による見送りもDBに残し、そのイベントの再配信や日付変更後に付与し直しません。

通話報酬は**サーバー・ユーザーごとに1日合計5時間分、最大300 NOT**です。日本時間00:00で上限をリセットし、再参加・チャンネル移動・Bot再起動でも当日の付与数を保持します。Botは通話に参加する必要がありません。Bot以外の参加者が対象で、1人だけの通話・ミュート中も含みます。退出時の1分未満は切り捨て、Bot停止・Gateway切断・所属確認失敗中の時間は遡って付与しません。起動・再接続時点ですでに通話にいる人も、その時点から計測します。日付は付与対象の1分を判定した時刻を使います。

`NotRepository.grant_reward(actor, reason, request_id, now)` は付与済みの取引を `Some(LedgerEntry)`、制限による見送りを `None` で返します。キーは `reward:{理由コード}:{元メッセージID}`、リアクションの場合は `reward:{理由コード}:{元メッセージID}-{リアクションした人のID}` です。絵文字はキーに含めず、取り外し・付け直し・別絵文字でも同じ結果を返します。日次上限・間隔・残高上限・処理済み判定と、種別に応じた報酬額の追記・処理結果の保存を同じImmediateトランザクションで確定します。返信・リアクションの各受取人の判定は独立しています。

Gatewayは `GUILDS | DIRECT_MESSAGES | GUILD_MESSAGES | GUILD_MESSAGE_REACTIONS | GUILD_VOICE_STATES` を使います。Botには対象チャンネルの閲覧と「メッセージ履歴を読む」を許可してください。リアクション先、イベントに参照元がない返信先はRESTで取得します。取得できない場合は付与せずエラーを記録します。Message Content・Guild MembersなどのPrivileged Gateway Intentsは不要です。[イベントとIntent](https://docs.discord.com/developers/events/gateway#list-of-intents)、[通話状態のイベント](https://docs.discord.com/developers/events/gateway-events#voice-state-update)

`NotRepository.grant_voice_reward(actor, earned_at)` は確認済みの通話1分へ1 NOTを付与します。既存の `ADJUSTMENT` 履歴と `voice:{日本時間の日番号}:{ユーザーID}:{Unix分}` キーを使い、同じ分の復元・当日300回の上限・残高検証・追記を同じImmediateトランザクションで行います。表・依存・スキーマの追加はありません。付与結果が不明な場合は獲得時刻を保持し、翌分になっても同じキーで照合します。履歴の理由表示は既存の「管理者による残高調整」を共用し、`voice:` で通話報酬を識別します。

自動検証では既存の実SQLite・ローカルHTTPのテストで、正負・0の調整、過大減算・整数上限超過、管理権限・対象所属、指定額の異なる依頼ID再利用、同時再試行、INSERT／COMMIT失敗時の取消、購入・返金・譲渡との残高競合を確認しています。実Discordでのコマンド反映・譲渡・増減指定・退会後の拒否は未確認です。テスト用サーバーで正の調整による加算、`amount:-100` による減算、残高50への `-100` の拒否と `-50` による0への減算、一般ユーザーの拒否を確認してください。

## コンテンツと商品操作

`SHOP_CHANNELS` に出品先の `ギルドID=販売チャンネルID` を設定し、Botへ販売チャンネルの「チャンネルを見る」「メッセージを送信」「埋め込みリンク」を許可してください。テキストチャンネル・アナウンスチャンネルを受け付けます。出品者には対象ギルドへの所属が必要で、管理者権限は不要です。

コマンドを使わずに出品できます。

1. BotとのDMへファイルを1つ送ります。
2. 「このファイルを出品する」を押し、出品先サーバーを選びます。
3. 商品名・説明・価格のフォームを送信します。
4. プレビューを確認し、「出品する」で保存・商品登録・公開を確定します。

サーバー候補は `SHOP_CHANNELS` の設定を25件ずつ照合し、Bot・本人の所属を確認できたものだけを表示します。「前へ」「次へ」でページを切り替えられます。候補のないページでも次のページへ進めます。公開商品には購入ボタンだけを表示し、出品はBotとのDMから始めます。

入力は本人ごとに1つ、5分間有効です。有効な添付の送り直し・`/content add`・取消・期限切れ・再起動で古い入力は失効します。フォームを閉じた場合や入力不正時は、元のボタンから期限内に入力し直せます。添付受信やフォーム送信だけではファイルを保存せず、P08と同じ最終プレビューへ進みます。

現在のBotは `GUILDS | DIRECT_MESSAGES | GUILD_MESSAGES | GUILD_MESSAGE_REACTIONS | GUILD_VOICE_STATES` を使用します。DMの添付はMessage Content Intentの例外なので、Privileged Gateway Intentsは無効のままで使えます。[DiscordのGateway Intent・DMの例外](https://docs.discord.com/developers/events/gateway#message-content-intent)

```text
/content add title:資料集 description:使い方をまとめたPDF price:500 guild:対象サーバー file:資料.pdf
```

`guild` はBot・本人の所属と販売チャンネル設定を満たす候補、またはサーバーIDを指定します。直接入力でも実行時に確認します。価格は正の整数文字列で受け取り、丸めません。添付は1ファイル・1バイト〜20 MiBです。Bot側の `CONTENT_DIR` は非公開な永続ディスクを指定してください。

入力後にサーバー名・ファイル名・価格のプレビューを返します。「出品する」で所属を再確認し、Discord添付を上限付きで取得・永続保存して商品を確定します。販売チャンネル・Bot権限は公開直前に確認し、商品情報と購入ボタンを公開します。「キャンセル」では保存・商品作成・公開を行いません。下書きは本人ごとに1つ、5分間有効で、新しい入力・期限切れ・Bot再起動で失効します。同じ下書きの保存・商品確定の再試行は同じ操作IDを使います。

公開に失敗した場合は `PublicationPending` と保存済みの商品ID、「再投稿する」ボタンを返します。再投稿は本人・所属を再確認して同じ商品を使い、Bot再起動後も操作できます。公開記録が確定済みなら同じメッセージを案内します。投稿だけ成功し公開記録が失敗した場合は表示が重複することがありますが、商品は増えません。原本・保存キー・元の添付URLは公開しません。

購入確認・決済・ファイル配送・購入一覧はP09、コマンドなしのDM添付・入力フォームはP10で接続済みです。

P08の実機確認は未実施です。テストギルドとBotとのDMで次を確認してください。

- コマンド・候補の表示、プレビュー後の出品、キャンセル・期限切れ・再起動による下書き失効。
- 販売チャンネル未設定・別ギルドのチャンネル・Bot権限不足・退会後の確定を拒否すること。
- 公開だけを失敗させた後に、権限を戻して「再投稿する」で同じ商品を公開できること。
- 上限サイズの添付を保持でき、公開メッセージにファイル本体・保存先・元URLが含まれないこと。

保存先を渡して `infrastructure::discord::shop::ShopRepository::new(directory)` を作り、`store_content` に認証済みの `Actor`、Botが発行した出品操作ID、元ファイル名、`Read` を渡して保存します。commandsが戻り値の `domain::StoredContent` と `ItemDetails` を `infrastructure::sqlite::shop::ShopRepository::create` に渡すと、ファイル情報・商品・初版を同じトランザクションで確定します。未保存の `ContentFile` だけから商品を作る入口はありません。

1商品1ファイル、正のサイズから20 MiBまでを受け付けます。Discordの既定のファイル上限に合わせ、25 MiBの送信リクエスト上限内にメタデータ用の余地を残します。元ファイル名はUTF-8で255バイト以内とし、保存パスには使いません。[Discordのファイル仕様](https://docs.discord.com/developers/reference#uploading-files)、[送信リクエスト上限](https://docs.discord.com/developers/resources/message#create-message)

保存先はBot専用の非公開な永続ディスクを指定してください。キーは `content-{guild_id}-{user_id}-{request_id}` で、操作IDは1〜128文字のASCII英数字・ハイフン・アンダースコアに限定します。同じ下書きの再試行ではIDを変えません。同じキーに別の内容が来た場合や、既存の保存先がシンボリックリンクの場合は拒否します。同期I/Oなので、非同期のイベント処理からは `spawn_blocking` で呼び、DBセッションを保持したまま呼ばないでください。

`ShopRepository::find` と `list` は対象ギルドの販売中の商品を返します。`update(actor, item_id, expected_revision, details)` と `delete(actor, item_id, expected_revision)` は出品者本人だけが実行でき、履歴の新版をINSERTします。出品者・ギルド・ファイルは変えません。作成の再試行は初版の内容と照合して現在の商品を返し、変更の再試行は期待する次の版と同じ内容ならその版を返します。異なる内容や版の競合は拒否します。削除済みへの新しい変更は拒否し、削除の再試行は成功として扱います。

商品削除やDB確定エラーでも完成ファイルは保持します。DB結果が不明な場合も同じ操作IDで再試行し、ファイルを消さないでください。確定されなかった完成ファイルや、プロセス強制終了時の `.pending-*` の自動削除は行いません。実Discordからの添付取得・公開はP08、購入後のDM配送はP09で接続済みです。

## 購入確認と決済

販売チャンネルの「購入する」から、本人のDMへサーバー名・商品名・出品者・価格・現在残高・購入後残高を送ります。「はい（500 NOTで購入）」で決済し、ファイルをDMへ送ります。「いいえ」、確認DMの拒否、確認期限切れでは課金しません。確定時には所属、ファイルを読めること、保存サイズとDMの添付上限も確認します。ボタン操作は外部照会より先に本人向けの受付応答を返します。

確認は5分間のメモリ保持で、二重クリックでは一度だけ受け付けます。Bot再起動後の未購入の確認は失効します。決済済みなら、元の「はい」から確認IDで購入結果を復元し、追加課金なしで再送できます。決済結果が不明な場合は「決済結果を確認する」を押してください。購入一覧にも履歴がなく未購入と確認できた場合に、新しい購入確認へ進みます。

配送できなかった場合は `DeliveryPending` と購入ID・無料再送ボタンを返します。DMを受け取れる状態に戻してボタンを押すか、BotとのDMで次を実行してください。

```text
/content purchases guild:対象サーバー
```

未返金の購入を新しい順に5件ずつ表示し、「前へ」「次へ」と各商品の「無料再送」を使えます。商品変更・削除後も受け取れます。再送のたびに本人・所属・未返金を照合し、追加課金はありません。送信結果が不明な場合は同じファイルが重複して届くことがあります。自動返金は行いません。

P09の実機確認は未実施です。出品者・購入者とテストギルドで次を確認してください。

- 購入者を1,200 NOTに調整し、500 NOTの商品を確認・購入すると、購入者700・出品者500になりファイルがDMへ届くこと。
- 「いいえ」、DM拒否、期限切れ、退会、原本の欠落では課金されず、二重クリックでも課金が1回であること。
- 決済後のDM拒否を解消し、再起動後の元の確認・購入一覧・無料再送で追加課金なく受け取れること。
- 商品削除後の再送、返金後・別人への再送拒否、上限サイズのDM配送、購入一覧のページ切替。

`ShopRepository::prepare_purchase(actor, item_id, request_id, now)` は、本人・ギルドに結び付いた5分間の `PurchaseQuote` を返します。`item()` に確認時の商品版と価格を保持し、確認発行では課金しません。確認IDはBot側で発行し、同じ確認の再試行では変更しません。

`purchase(actor, &quote, now)` は、同じ確認IDで確定済みかを先に照合します。初回だけ期限、最新の版・価格、販売状態、コンテンツの自己購入・購入済み、残高を検証してImmediateトランザクションで確定します。コンテンツは購入者の減算と出品者の加算を一括記録します。ロールは購入者の減算だけです。価格を元に戻しても版が変わっていれば再確認が必要です。

`now` はコマンドやボタンの受付時に呼び出し側が `SystemTime::now()` で採取したサーバー時刻を渡し、利用者が指定した時刻を使いません。期限ちょうどで未処理の確認は失効します。確定済みなら期限・商品変更・削除・後続の残高変更で再課金せず、元の取引を返します。確認IDが同じでも購入者・商品・金額が異なれば `RequestConflict`、コンテンツ売買の片側欠落などの不整合は `InvalidData` になります。

`PurchaseResult` の `buyer()` は購入取引、`seller()` は `Option<&LedgerEntry>` の売上取引、`item()` は現在の商品状態です。新しいロール購入の売上は `None` です。実際の支払額には `buyer().amount()` を使い、現在の商品価格から計算し直しません。この結果だけで配送を許可せず、以下の購入権限照会を使います。ファイル確認・DM配送はP09で接続済みです。

## 購入結果の復元・再送権限・返金

- `find_purchase_by_confirmation(actor, confirmation_id)`：本人・対象ギルドの領収結果を復元します。未処理なら `None`。返金済みでも元の取引を返し、課金行を増やしません。
- `list_purchases(actor)`：本人の未返金購入を購入IDの降順で返します。既存の `PurchaseResult` を使い、商品変更・削除後も一覧に含めます。
- `get_content_for_purchase(actor, purchase_id)`：購入者・ギルドと購入／売上／返金の整合性を照合し、配送用の `ContentFile` を返します。購入IDには `PurchaseResult::buyer().id()` を使います。返金済み・別人には取得を許可しません。
- `refund(actor, purchase_id, request_id)`：NOT管理権限を持つ実行者だけが元の購入額を返金します。元の売上がある場合だけ売上取消も一括追記します。`RefundResult::buyer()` は返金取引、`seller()` は売上取消がある場合の `Some`、なければ `None` です。

返金キーは `refund:{request_id}:buyer`・`refund:{request_id}:seller`。売上なしのロール購入には購入者側だけを記録します。同じ依頼ID・購入の再試行は、残高が後から変わっても元の結果を返します。同じIDを別購入に使うと `RequestConflict`、別IDによる二重返金は `AlreadyRefunded` です。購入者の残高上限超過・途中のSQL失敗、売上取消がある場合の出品者の残高不足では、全体を取り消します。

返金後も領収結果の復元はできますが、配送権限は失われます。ファイル自体は削除しません。配送の直前に権限を確認し、返金や配送失敗を理由に同じ確認IDで購入をやり直さないでください。

## 商品管理・返金

BotとのDMで操作します。商品IDと現在の版は公開Embedの末尾、購入IDは領収結果や `/content purchases` で確認します。ID・版・価格は整数文字列です。

```text
/content update guild:サーバーID item:商品ID revision:現在の版 title:変更後の商品名 description:変更後の説明 price:800
/content delete guild:サーバーID item:商品ID revision:現在の版
/content republish guild:サーバーID item:商品ID
/content refund guild:サーバーID purchase:購入ID
```

変更・削除・再投稿は対象サーバーに所属する出品者本人だけが実行できます。変更では名前・説明・価格をすべて指定し、原本・出品者・対象サーバーは変更しません。古い版による競合は拒否します。同じ版・同じ内容の再試行は既存の更新結果を返し、削除の再試行で販売を再開することはありません。

最新の公開記録にあるメッセージを編集し、成功した版とメッセージIDを追記します。Discordでメッセージ自体が消えている場合は投稿を作り直します。変更・削除・公開は商品ごとのロックで直列化します。ロックはBotプロセス内のため、運用では同じDBに対するBotを1プロセスだけ起動してください。

過去の公開商品に残る「出品する」ボタンは、Botを再起動した後、出品者本人がDMで `/content republish guild:サーバーID item:商品ID` を実行すると削除されます。

表示の反映に失敗してもDBの更新は確定済みです。`PublicationPending` の商品IDと再投稿ボタン、または `/content republish` で最新状態へ同期します。削除後は購入ボタンを「販売終了」にして無効化し、古い表示からの購入もDBで拒否します。価格・版が変わる前の購入確認では決済できず、現在価格で確認し直す必要があります。商品削除だけでは購入済みの再送権限は失われません。

返金は対象サーバーの所有者または `ADMINISTRATOR` を持つメンバーだけが実行できます。変更後の価格ではなく元の購入額を返し、元の売上があれば同時に取り消します。売上のある購入は出品者が残高不足なら返金できません。売上なしのロール購入は出品者の残高を変更しません。同じInteractionの再処理では二重反映せず、別の返金操作で既に返金済みなら拒否します。返金で停止できるのは以後のBotからの再送で、送信済みファイルは回収できません。

## ロール販売・復旧（P13）

サーバー所有者または `ADMINISTRATOR` を持つメンバーが、既存のロールを登録します。公開先はコンテンツと同じ `SHOP_CHANNELS` を使います。

```text
/role add role:ロールID title:会員権 description:会員向けチャンネルの閲覧 price:500 guild:サーバーID
/role recover guild:サーバーID
```

サーバー内では `guild` を省略でき、DMでは必須です。Botには「ロールの管理」と、販売対象より上位のロールが必要です。`@everyone`・外部サービスの管理ロール・Bot以上のロールは販売できません。[Discordのロール操作](https://docs.discord.com/developers/resources/guild#add-guild-member-role)と[権限階層](https://docs.discord.com/developers/topics/permissions#permission-hierarchy)に従って照合します。

公開商品の購入ボタン→DMで価格確認→購入確定という既存の導線で決済し、COMMIT後にロールを付与します。購入者から代金を減らし、出品者には加算しません。出品者本人も価格以上の残高があれば購入でき、代金を支払います。確認DMも減算後の残高を表示し、返金では元の購入額だけを戻します。既にロールを持つ人・権限不足は決済前に拒否します。商品変更・削除・再投稿・管理者返金は `/content update`・`delete`・`republish`・`refund` を共用します。`/content purchases` にもロール購入が表示され、「ロール再照合」で復旧できます。

付与APIが失敗しても、保有を確認できれば成功とします。未保有を確認した場合は元の購入額の返金を試みます。売上なしのロール購入は出品者の残高に依存せず返金します。保有状態が不明、購入者の残高上限超過やDB障害などで返金できない場合は `RoleDeliveryPending` と購入IDを案内し、未返金の購入権限を残します。追加購入せず、再照合ボタンか `/role recover` を使ってください。Bot起動時にも未返金のロール購入を照合・再付与します。コンテンツファイルの配送失敗は無料再送で復旧し、自動返金しません。

変更前に確定した売上付きロール購入の履歴・残高は書き換えません。同じ購入確認からの復元は元の取引を返し、返金では元の売上も取り消します。テーブル・移行SQLの追加は不要です。

ロールの管理者返金では解除を確認してから返金します。返金が成立しなかった場合は権利を残し、ロールの復元を試みます。復元を確認できない場合は `/role recover` または再起動で照合してください。Discord操作とDB確定は一括処理にはできず、サーバー管理者による外部のロール変更も含め、最終状態の照合が必要です。同じDBに対するBotは1プロセスで運用します。

自動検証ではDiscord操作の4件と実SQLiteの2件で、権限・階層・二重確定・付与失敗時の返金・再起動後の復旧・返金不能時の権利維持を確認します。売上のない購入と返金、出品者の残高上限、本人の購入と確認DM、旧仕様の売上付き履歴の復元と返金も検証対象です。依存・設定・テーブルの追加はありません。

## 運用・バックアップ・復元

リポジトリのルートを作業ディレクトリにして起動します。相対パスの設定はこのディレクトリ基準です。

```sh
cargo build --release --locked
set -a
. ./.env
set +a
exec ./target/release/notbot
```

常駐運用ではプロセス管理ツールにも同じ作業ディレクトリ・環境変数を設定し、標準出力と標準エラーを保存します。Ctrl-CまたはSIGTERMで終了を待ち、同じ設定・DB・コンテンツで再起動してください。再起動すると未確定の出品・購入確認は失効します。決済済みの購入権限はDBに残り、購入一覧から無料再送できます。

バックアップはBotと同じDB・コンテンツに書き込む処理をすべて停止してから行います。既定パスなら、終了を確認した後に次を実行します。DBと原本は必ず同じ停止時点の組で保管し、片方だけを復元しないでください。

```sh
umask 077
notbot_backup="backups/$(date +%Y%m%d-%H%M%S)"
mkdir -p "$notbot_backup"
cp -a data "$notbot_backup/data"
```

`DATABASE_PATH`・`CONTENT_DIR` を変更した場合は、それぞれの保存先を同じバックアップへコピーします。SQLiteの `-wal`・`-shm` が残っていればDBと一緒に保管してください。コピー中はBotを起動しません。`.env` の設定は秘密情報として別途管理し、バックアップも非公開にします。

復元も停止中に行います。上書きで混在させず、現在の `data` を別名へ退避してから、選んだバックアップの `data` をリポジトリ直下へコピーします。独自パスでもDBと原本を両方置き換え、Bot実行ユーザーの所有権・アクセス権を維持してください。起動後は残高・購入一覧・商品削除状態を照合し、購入済みファイルを無料再送してDBと原本の組を確認します。バックアップ以降の決済・返金は復元されないため、Discord上の送信済みメッセージだけを根拠に再課金しないでください。

調査では次のIDを使います。ログはトークン・原本の保存先・添付URL・外部エラー本文を出しません。

| 識別子 | 表示・ログ | 用途 |
|---|---|---|
| 商品ID | Embed末尾、`item=` | 更新・公開保留・再投稿の照合。`revision=` は商品版。 |
| 確認ID | 決済照合ボタン、結果不明時の返信、`confirmation=` | 例 `100-911`。同じ確認から領収結果を復元する。 |
| 購入ID | 領収結果・購入一覧、`purchase=` | 無料再送・配送保留・返金対象の照合。 |
| 返金依頼ID | `content refund` の `request=` | 返金を実行したInteractionと取引行の照合。 |

`publication_pending`・`settlement_pending`・`delivery_pending` はそれぞれ公開・決済結果・配送の確認が必要な記録です。`role delivery_pending`・`reconcile_failed`・`restore_pending` はロールの照合・復旧に使います。返信に失敗した場合にも購入一覧で課金済み状態を確認し、決済結果不明の操作は同じ確認ボタンで照合します。

「Discord: イベントの処理に失敗しました。」には、イベント名の `event=` と、APIが失敗した場合の `HTTP=`・`code=` を記録します。DBの失敗は業務エラーの種類、ファイルI/Oの失敗はエラー種別を記録します。原因調査にはこの行と発生時の操作を使い、トークン付きURL・APIの応答本文・イベント全体はログへ出しません。

## 依存ライブラリ

`Cargo.toml` では主要ライブラリのバージョンを固定し、`Cargo.lock` で依存全体を固定しています。

| 用途 | ライブラリ | バージョン |
|---|---|---|
| 非同期ランタイム | Tokio | 1.53.3 |
| Discordコマンド | Poise | 0.7.1 |
| 添付の上限付き取得 | reqwest | 0.12.28 |
| Discord API | Serenity | 0.12.5 |
| ORM・SQLite | SeaORM | 2.0.4 |
| エラー表示・変換の生成 | thiserror | 2.0.21 |

起動・Discord処理は[JadeMusicの起動処理](https://github.com/segfau-yama/JadeMusic/blob/main/src/main.rs)を参考に、共通の `Box<dyn Error + Send + Sync>` と `?` で失敗を返します。定型的な `Display`・ラップするだけの `From` は [thiserror](https://github.com/dtolnay/thiserror)に任せ、返信失敗はイベント入口でまとめて扱います。thiserrorは既存の間接依存を直接依存として宣言したもので、依存パッケージの追加・バージョン変更はありません。

## 設計と実装手順

コードもドメイン層（検証済みデータの保持）とインフラ層（変換・検証・操作・I/O）の2層へ整理しています。共通型は `domain::`、操作・DB・Discord・ファイル処理は `infrastructure::` を使います。旧 `application::` とDB向けTrait・型引数は削除しました。インフラ内は `sqlite/` にDBと操作処理、`discord/` にPoiseのコマンド・イベント・認証・ファイル保存をまとめています。各Repositoryは相互に参照せず、commands／eventsがドメイン値を受け渡します。Discordの返信・対話・ロール操作はcommands、Gateway処理はeventsに置きます。配置は[アーキテクチャ設計](design/ARCHITECTURE.md)を参照してください。
