## 共通の実装方針

- 設計上はドメインとインフラの2層。ドメインは共通型と値の不変条件、インフラは変換・認証・操作処理・DB・Discord・ファイルI/Oを担当する。`NotUseCase`・`ShopUseCase` はインフラの操作処理として置き、その名前だけを理由に独立した層を作らない。
- Rustの1つのcrate、非同期ランタイムはTokio、DiscordはPoise＋Serenity、DBはSeaORM＋SQLiteから始める。採用版と必要なfeatureをP00で確認し、`Cargo.lock` を管理する。
- 通常の業務データ変更は全テーブルINSERTのみ。現在状態はVIEWから求める。SeaORMの `save`・UPDATE・DELETE・REPLACEで商品や残高を変更しない。
- API・ORMのモデルは具体実装内で使う。内側の型へ必要な値を渡す処理は、その場の関数・コンストラクタで済ませる。
- 認可・価格・残高・冪等性はユースケースで判断する。Discordへの送信とファイルI/OはDBトランザクションの外で行う。
- 新しいDB向けの実装、Web、OAuth、DIコンテナ、汎用Repository、変換専用層、配送キューは追加しない。ファイル保持も具体的な永続ディスクへの処理から始める。
- テストは実装した関数・ユースケースを呼ぶ。金額と権限の経路は実SQLiteで確認し、別言語に同じ業務ロジックを書き直したものを実装のテストにしない。

## P02: 実DBとトランザクション

**対象**：`NewLedgerEntry`、`src/infrastructure/sqlite/mod.rs`・`src/infrastructure/sqlite/001_initial.sql`、起動処理、`tests/sqlite_flows.rs`。

- DB設計の7テーブル・3VIEW・取引理由の初期値・CHECK／FK／一意制約を、実行するマイグレーションへ移す。設計書から起動のたびにSQLを抽出する構成にはしない。
- マイグレーションは適用済みかを管理し、再起動で初期値を重複挿入しない。マイグレーション実行基盤がトランザクションを管理する場合は、設計SQLの `BEGIN`・`COMMIT` を入れ子にしない。
- 読み書き開始・残高取得・取引追記・確定／取消は `SqliteDatabaseAccess`・`SqliteSession` の通常メソッドを使う。以後必要になる照会は各工程で追加する。
- 各接続で外部キーを有効にする。`begin_write` はSQLiteのImmediateモードを指定し、残高確認から追記まで同じトランザクションを使う。
- `begin_read` の追記拒否、途中失敗・未確定セッション破棄時の全体取消、競合・不正データ・結果不明のエラー変換を実装する。

SeaORMには `TransactionOptions.sqlite_transaction_mode` と `SqliteTransactionMode::Immediate` を使うAPIがある。採用版でこの経路を確認する。プールへ直接 `BEGIN IMMEDIATE` を送り、その後別に借りた接続で操作する実装にはしない。[SeaORMのトランザクションAPI](https://docs.rs/sea-orm/latest/src/sea_orm/database/connection.rs.html)

**完了条件**：マイグレーションを再実行しても壊れない。空の残高が0、追記後のVIEWが正しい。不明なreason・不正な金額・重複event_keyを拒否する。実ファイルのDBを2つの接続から使い、片方の書き込みが確定する前に他方が同じ残高で書き込み判断できないことを確認する。

実装は適用版をSQLiteの `user_version` へ記録し、DDL・VIEW・初期値・版番号を1つのImmediateトランザクションで確定する。SQLはコンパイル時に同梱し、設計書からの起動時抽出はしない。通常の追記APIは金額・理由・参照を保存するだけで、残高不足・管理権限・二重依頼の結果照合などの業務判断はP03以降に加える。

## P03: 残高と残高調整

**対象**：`src/infrastructure/sqlite/not.rs`、DB照会・追記、実DBテスト。

**完了条件**：別ギルドの残高が混ざらず、無権限の調整・同じ依頼の重複反映を拒否できる。ランキングと目標残高への調整を実DBで確認できる。

## P04: ファイル保持と商品

**完了条件**：商品作成の再試行で重複商品を作らず、版の競合・他人による変更・保存領域外へのパスを拒否する。削除で履歴を消さず、販売中一覧からだけ外れる。BotがDMへ再送できないサイズのファイルを商品として確定しない。

## P05: 確認価格での購入

**対象**：`PurchaseQuote`、`ShopUseCase.prepare_purchase`・`purchase`、購入関連のDB照会。

- 確認ID・購入者・ギルド・商品版・価格・5分の有効期限を持つ確認を作る。ここでは課金しない。
- 確定時は同じ確認IDの確定済み取引を先に探し、初回だけ期限・版・価格・販売状態・自己購入・購入済み・両者の残高を検証する。
- `PURCHASE` と `SALE` を同額・逆符号で一括INSERTする。売上は元の購入を参照する。
- イベントキーは `content:{quote_id}:buyer`・`content:{quote_id}:seller`。結果不明時もこのキーで照合する。受取側の残高上限もchecked演算で検証する。

**完了条件**：1,200NOTから500NOTの商品を買うと購入者700・出品者500になる。同じ確認の再試行、別確認からの同時購入、価格変更、期限切れ、別人・別ギルド、残高不足、2行目の失敗を実DBで確認する。確定済みなら期限や商品変更を理由に再課金しない。

実装では `prepare_purchase` と `purchase` に受付時のサーバー時刻 `now: SystemTime` を渡す。期限は受付時刻＋300秒とし、時計用のTraitや設定は追加しない。`PurchaseQuote` は商品スナップショットにギルド・版・価格を保持する。`PurchaseResult` は現在の商品と元の購入・売上の2行を直接持ち、支払額を現在の商品価格から計算し直さない。配送権限と確認IDだけからの復元はP06で追加する。

## P06: 返金と購入権限

**対象**：`find_purchase_by_confirmation`・`refund`・`list_purchases`・`get_content_for_purchase`、対応するDB照会。

- 確認IDから本人の確定済み結果を復元する。返金済みでも同じ確認IDで再購入しない。
- 購入者とギルド、未返金の購入を照合して、購入一覧と配送用ファイル情報を返す。
- 返金は認可を確認し、元の購入額を使って購入者への返金と出品者の売上取消を一括INSERTする。二重返金と出品者の残高不足を拒否する。

**完了条件**：DBを閉じて開き直しても、同じ購入を復元できる。商品削除・価格変更後も元の購入者は再送権限を持ち、別人は取得できない。返金後は再送不可となり、両者の残高が正しく戻る。権限照会・再送準備では課金行が増えない。

実装では返金の認可に既存の `Actor.can_manage_not` を使う。同じ `refund:{request_id}:buyer`・`:seller` の再試行は元の返金結果を返し、別IDでの二重返金は拒否する。購入一覧は未返金の `Vec<PurchaseResult>`、返金結果は2行を持つ `TradeResult` とし、別の `PurchasedItem` 型は追加しない。購入一覧と配送権限は購入・売上・返金の両行を照合し、不完全な履歴では配送を許可しない。実ファイルの読取り・DM配送はP09で接続する。

## P09: DM確認・購入・配送・再送

**対象**：購入・はい／いいえ・再送のボタン処理、確認状態、`/content purchases`。

- ギルドの購入ボタンからP05の確認を作り、本人のDMへサーバー名・価格・残高・購入後残高を表示する。DM送信失敗時は課金しない。

- 配送失敗は `DeliveryPending` として購入IDを示す。購入一覧と再送ボタンから追加課金なしで再送できるようにする。自動返金しない。
- 再起動後の未購入の確認は失効させ、確定済みなら確認IDから復元する。DBセッションや確認状態のロックを保持したままDiscord APIを待たない。

**完了条件**：「いいえ」・DM拒否では課金されず、「はい」の二重クリックでも課金は1回。決済後の送信失敗・再起動・結果不明から追加課金なく再送でき、返金済み・別人への再送を拒否できる。Discordの応答期限内に受付応答できる。

## P10: コマンドなしの出品導線

**対象**：DMの添付受信・出品ボタン・サーバー選択・入力フォーム。

- DMで1ファイルを受け取ると、本人向けに「このファイルを出品する」を提示する。送っただけでは公開しない。
- サーバー選択と商品名・説明・価格のフォームをP08と同じ下書きへ接続する。作成・検証・保存・公開の処理を別に作らない。
- 入力途中の取消・期限切れ・再起動・別ユーザーによる操作を扱う。候補が多ければ検索やページ分割する。
- 出品の入口はBotとのDMに集約し、ギルドの公開商品には購入ボタンだけを置く。初期実装でモーダルの新しい添付機能へ切り替える必要はない。

**完了条件**：コマンドを入力せず、DM添付から商品公開まで進める。未確定のファイルや下書きが公開されず、コマンド経由と同じ商品・検証結果になる。

## P11: 商品管理とコンテンツ売買の通し確認

**対象**：商品変更・削除・再投稿・返金の操作、README、実機検証記録。

- 出品者の変更・削除をP04、認可された返金をP06へ接続する。Discord上のコマンド名は既存の `/content` に合わせる。
- 最新の公開記録を使って商品Embedを編集する。商品ごとに公開処理を直列化し、削除時は新規購入を止める。編集・再投稿失敗でもDBの権限と価格を優先する。
- テスト用の出品者・購入者で「調整によるNOT供給 → 出品 → 公開 → DM確認 → 購入 → 受取 → 無料再送 → 変更・削除 → 返金」を確認する。
- Botを停止してDBとコンテンツを一緒にバックアップ・復元する手順、Bot再起動、ログで使う商品ID・確認ID・購入ID、運用時の起動方法をREADMEへ記載する。

**完了条件**：[コンテンツ売買の完成条件](#コンテンツ売買の完成条件)を満たす。自動検証と実機検証の結果を分けて記録し、未実施の確認を通過扱いにしない。

## P12: 既存のNOT報酬・罰則・譲渡

**対象**：`grant_reward`・`adjust_amount`・`transfer` と投稿・リアクション・返信等のイベント処理。

**現在の内訳**：報酬・増減指定・譲渡のDB操作、報酬イベント処理と `/not adjust`・`transfer` は実装・自動検証済み。罰則と調整はユーザーの指示で `/not adjust amount:正負の整数` に統合した。実Discordでの確認は未実施。

ユーザーが以下の案を承認したため、報酬仕様として確定した。上限判定はBotでの受付時刻を使う。日次上限と60秒間隔は付与済みの報酬だけを数え、見送ったイベントの処理結果もDBへ残す。返信者の投稿報酬と返信先への報酬、リアクションの両受取人の報酬は独立して判定する。

| 確認項目 | 確定した仕様 | 状態 |
|---|---|---|
| 投稿・リアクション実行者・リアクション受信者・返信受信者の付与額 | 順に5・1・10・20 NOT | 承認済み |
| 回数上限・集計期間・最短間隔と、その適用単位 | サーバー・受取人・報酬種別ごとに60秒に1回、1日100回まで。日付は日本時間で区切る | 承認済み |
| Botの投稿・操作と自己リアクション・自己返信を対象にするか | Bot・Webhook・自己リアクション・自己返信を対象外にする。自己返信、Bot・Webhookへの返信は投稿報酬も対象外 | 承認済み |
| リアクション再追加・同一投稿への複数絵文字を別報酬にするか（イベントキーの単位） | 同じ投稿への同じ人のリアクションは絵文字や付け直しによらず1回。投稿・返信は各メッセージIDで重複排除 | 承認済み |

- まず報酬額、回数・間隔、Bot・自己操作の扱い、イベントキーの単位を仕様として明記する。現在の設計書に具体値がない報酬・制限は推測で決めず、その項目だけユーザーへ確認する。コンテンツ売買の完成はこれに依存させない。
- 管理者の増減指定は `/not adjust` に統合し、正負の整数額を自由に指定する。増減後の負の残高・整数上限超過を拒否する。譲渡は100・500・1,000NOTとし、自己譲渡・残高不足を拒否し、送受信の2行を一括追記する。
- Discordイベントの再配信で報酬を重複させない。報酬の制限も同じ書き込みセッションで照合する。

**完了条件**：同じイベントの再処理、上限・間隔、正負の調整と過大減算の拒否、送受信途中の失敗を確認できる。購入・返金と並行しても負の残高や二重反映が発生しない。

## P13: ロール販売の後続実装

**対象**：`ItemTarget::Role`、インフラのSerenityによるロール付与・照合・復旧。

- 既存の売買ルールを使い、COMMIT後にインフラのDiscord処理からロールを付与する。SDK固有の型はドメインへ持ち込まない。`DiscordAccess` Traitや追加の型引数は作らない。
- 結果不明時はロール保有を照合する。従来設計どおり返金を試み、返金できなければ配送保留として復旧する。
- コンテンツ配送失敗時の無料再送と、ロール配送の返金・復旧を混同しない。

**完了条件**：自己購入・権限不足・ロール付与失敗・結果不明・Bot再起動からの復旧を確認する。コンテンツ売買の既存テストも通る。

## 各工程の共通チェック

P00以降は、変更範囲に必要なテストを追加して次を実行する。毎回のDiscordへの実送信や大量の全組み合わせテストは要求しない。

```sh
cargo fmt --all -- --check
cargo clippy --locked --all-targets -- -D warnings
cargo test --locked --all-targets
```

SQL・取引境界のテストは実SQLiteを使う。2接続の競合・再起動は一時ファイルのDBで試し、接続ごとに別DBとなるメモリDBで代用しない。Discord APIの呼び出しを伴わない表示・入力処理は自動検証し、実機確認が必要なものは分ける。

実機確認にはBotトークン・テストギルド・販売チャンネル・出品者と購入者が必要。未提供でもオフラインで可能な実装・検証は進める。該当工程は「実機確認待ち」とし、後続の独立した作業まで止めない。

工程を終えたら、この文書の進捗表を更新し、変更点・実行したコマンドと結果・実機の未確認項目・次の工程を報告する。

## コンテンツ売買の完成条件

- [ ] コマンドと、DM添付＋フォームの両方から出品できる。
- [ ] 公開商品にファイル本体・元URL・保存キーが含まれない。
- [ ] 本人・ギルド・確認価格・商品版・期限を照合して購入する。
- [ ] 同じ確認・別確認・再起動後の再操作で二重課金しない。
- [ ] 価格変更・自己購入・残高不足・別人・別ギルドを拒否する。
- [ ] 購入・売上、返金・売上取消がそれぞれ一括確定する。
- [ ] 決済前のDM失敗は課金なし、決済後の失敗は無料再送で復旧できる。
- [ ] 商品削除後も既存購入者は再送でき、返金後は再送できない。
- [ ] 通常業務で既存行を変更せず、残高と最新商品状態をVIEWから取得する。
- [ ] DB・保持ファイルを復元した環境で購入権限と再送を確認できる。

完了マークは実装と検証の証拠が揃ってから付ける。機能の進捗は冒頭の表と検証記録を参照する。2層への構成変更は検証記録で確認し、未実施の実機確認を完了扱いにしない。
